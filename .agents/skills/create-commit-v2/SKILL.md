# Create Commit（提交變更）

依這門課的提交訊息慣例，把使用者目前的變更完成一次提交（commit）。

## 提交訊息格式

格式：`類別: 中文描述`（英文類別＋半形冒號＋一個空格＋中文描述）

1. 類別（四選一）：`feat`、`fix`、`docs`、`chore`——意思與分支類別相同，只是 `feature` 在提交訊息裡慣例簡寫成 `feat`。
2. 描述用中文、動詞開頭，一句話講清楚「這次改動做了什麼」，讓人不用開啟程式碼也大致看得懂。
3. 一次提交只講一件事。如果訊息想寫出「順便」兩個字，代表這次提交混了不只一件事。

## 執行步驟

1. 先用 `git status` 與 `git diff` 看清楚這次實際改了什麼；若發現和任務無關的變更混在裡，先向使用者確認要不要一起提交。
2. 把變更加入暫存區（staging area）：`git add .`（或只加入相關檔案）。
3. 依「實際的變更內容」產生提交訊息（不是依使用者的原話照抄），執行 `git commit -m "訊息"`。
4. 回報這次使用的提交訊息，讓使用者確認格式與內容。

## 不要做

以下的事不在這個 skill 的範圍內。提交完成、回報完訊息，這次任務就結束了，下一步等使用者開口：

- 不要順手推送（push）、開分支或發拉取請求。
- 不要主動修改或補寫任何檔案內容；這個 skill 只負責把「已經改好的東西」提交起來。
- 不要用改寫歷史的方式補救（例如 `git commit --amend`）；訊息或內容有誤，告訴使用者後用一次新的提交修正。
- 只執行這些指令：`git status`、`git diff`、`git add`、`git commit -m`、`git log`。清單以外的 git／gh 指令一律不執行。

## 範例

好的提交訊息：

- `feat: 將 W1 進度標記為完成`
- `fix: 修正登入按鈕顏色`
- `docs: 補充 README 安裝說明`

不好的提交訊息：

- `update`、`修好了`（看不出改了什麼）
- `改了 data.js`（只講動到哪個檔案，沒講做了什麼事）
- `標記完成順便修了排版`（一次講了兩件事）
